# 06. 내용 보강: 개선 확인 목록 (Improvement Checklist)

1차 사이트를 완성한 뒤 내용을 보강하는 단계의 작업 문서다. 개선 검토 요청이 들어오면 이 문서에 항목을 등록하고, 검토 결과와 반영 방향을 기록한 뒤 반영한다.

## 처리 절차

1. **등록:** 요청을 받으면 `IMP-번호`를 붙여 아래 확인 목록에 한 줄을 추가한다. 요청 원문은 항목 기록의 "요청"에 그대로 적는다.
2. **검토:** 해당 위치의 현재 내용, 논문 근거(§, Fig.), 다른 파트와 문서에 미치는 영향을 확인한다. 검토 방향 4가지 중 하나를 고르고, 근거와 반영안을 적는다.
3. **승인:** 검토 결과를 보고하고 반영 여부를 확인받는다. 승인 전에는 사이트와 문서를 고치지 않는다.
4. **반영:** 반영안대로 고치고, 빌드·린트·화면 확인을 한 뒤 커밋한다. 커밋 해시를 항목에 적는다.

## 검토 방향 (4종)

| 코드 | 방향 | 언제 고르나 | 주로 바뀌는 파일 |
|---|---|---|---|
| **A** | 슬라이드 추가 후 내용 보강 | 한 파트에 새 개념이 둘 이상 몰려 있거나, 청중이 알아야 할 선행 개념이 빠져 있을 때 | `sections.tsx`(파트 추가), 필요하면 `src/demos/`, `03_outline.md`(목차·시간), 번호가 밀리는 모든 참조 |
| **B** | 단순 내용 수정 | 파트 구성은 맞고 문장, 용어, 수치, 표현만 고치면 될 때 | `sections.tsx`, 해당하면 `03_outline.md`, `01_paper/` |
| **C** | 발표 대본에만 반영 | 화면에 둘 필요 없이 말로 전하면 충분할 때 (안내, 전환 멘트, 비유, 강조) | `07_script.md`만 |
| **D** | 개선 불필요 | 이미 반영되어 있거나, 바꾸면 논문 근거나 범위 규칙에 어긋나거나, 효과보다 비용이 클 때 | 없음 (이유만 기록) |

- 한 항목에 방향은 하나만 고른다. 화면 수정과 함께 대본에 멘트를 추가하는 일은 A·B에 딸린 작업으로 같이 적는다.
- 모든 반영은 범위 규칙을 지킨다. 2019 논문에 없는 내용은 넣지 않고, 이후 작업은 "리뷰 범위 밖"으로만 언급한다.

## 위치 표기

- 파트는 **Part 번호**로 적는다. Part 번호는 0부터 시작하고, Deck의 슬라이드 번호는 1부터 시작한다(**슬라이드 번호 = Part 번호 + 1**). 예: "3페이지" = Deck 3/11 = Part 2.
- 화면 요소는 `lead`(핵심 메시지), `points`(요점), `detail`(세부), `Demo`(인터랙티브 장치)로 구분한다. 모두 `frontend/src/content/sections.tsx`의 필드 이름이다.

## 항목 기록

### IMP-001 · 표지의 "Draco처럼 설계했습니다" 문구

**요청 (2026-10-11)**
> "이 사이트도 Draco처럼 설계했습니다." 라는 문구는 대본으로 가야 맞고 실제로는 Draco 철학을 반영했다라든가, 아무튼 정제된 표현을 사용하면 좋을 것 같다.

**현재 상태**
- Part 0 `points`의 셋째 줄: "이 사이트도 Draco처럼 설계했습니다. 위에서 **보기**와 **상황**을 바꾸면 각 보기가 어떤 soft constraint를 지키거나 위반하는지 보여 줍니다."
- 같은 표현이 `docs/03_outline.md`의 "0. 표지"와 `README.md`의 소개 문단에도 있다.

**검토**
1. **말투:** 앞 문장은 발표자의 소개 멘트이고, 뒤 문장은 조작 안내다. 둘 다 말로 전하는 편이 자연스럽고, 표지 화면에는 논문 제목, 저자와 같은 무게의 정보만 남기는 게 맞다. 요청에 동의한다.
2. **정확성:** "Draco처럼 설계했다"는 실제보다 크게 들린다. 이 사이트는 ASP나 Clingo로 보기를 고르지 않는다. 빌린 것은 **비용 모델**(위반한 soft constraint의 weight 합으로 순위를 매기는 방식, §4.2.2)이고, weight는 손으로 정했다. 화면 문구는 빌린 범위를 정확히 말해야 한다.
3. **"철학"이라는 표현:** 뜻이 넓어서 무엇을 반영했는지 드러나지 않는다. "비용 모델" 또는 "soft constraint와 weight로 평가한다"처럼 구체적으로 쓰는 쪽을 권한다.
4. **순서 문제:** 청중은 표지에서 아직 soft constraint를 모른다. 화면에는 짧게 예고만 하고, Part 5(Soft constraints와 비용)에서 토스트를 다시 가리키며 설명하는 흐름이 좋다.

**결정: B 단순 내용 수정** (원래 문구는 대본으로 옮김)

**반영안**
- Part 0 `points` 셋째 줄을 다음으로 바꾼다.
  > **메타 장치:** 이 사이트의 세 가지 보기(Paper · Deck · Explorer)를 Draco의 비용 모델로 평가합니다. 위반한 soft constraint의 weight 합이 비용입니다(weight는 이 사이트용으로 정한 값).
- `07_script.md` Part 0에 대본을 추가한다.
  > "이 사이트도 Draco처럼 만들어 봤습니다. 화면 위에서 보기를 바꾸면 오른쪽 아래에 이 보기가 어떤 디자인 규칙을 어겼는지, 그래서 비용이 얼마인지 나옵니다. 이게 무슨 뜻인지는 Part 5에서 다시 보겠습니다."
- `07_script.md` Part 5에 연결 멘트를 추가한다.
  > "처음에 보신 오른쪽 아래 토스트가 바로 이 계산입니다. 지금은 발표 상황이라 Deck의 비용이 가장 낮습니다."
- `docs/03_outline.md` "0. 표지"의 안내 문구와 `README.md` 소개 문단의 "Draco처럼 설계했습니다"도 같은 취지로 고친다.

### IMP-002 · Vega-Lite 소개가 명세보다 먼저 와야 함

**요청 (2026-10-11)**
> 3페이지에 vega-lite 명세가 등장하는데, vega-lite에 대한 설명이 먼저 있어야 청중의 이해를 수월하게 할 수 있다.

**현재 상태** (Part 2 "시각화를 쓰는 언어: Vega-Lite", Deck 3/11)
- `lead`: "차트 = data + mark + encoding. Draco는 Vega-Lite 명세를 logical facts로 옮겨 추론한다."
- `points`: encoding과 channel / type, aggregate, bin / JSON을 facts로 평탄화
- `Demo`: Vega-Lite JSON과 ASP facts를 나란히 놓은 코드 쌍(Fig. 2)과 막대 차트
- 앞 파트(Part 1)는 문제 제기라서, Vega-Lite가 무엇인지는 사이트 어디에도 설명되어 있지 않다.

**검토**
1. **요청이 맞다.** Part 2 한 장에 처음 보는 언어가 둘(Vega-Lite JSON, ASP facts) 동시에 나온다. 이는 `03_outline.md`의 서사 원칙 2("각 파트에는 하나의 메시지")에도 어긋난다. 청중은 JSON을 읽는 법을 모른 채 facts와의 대응을 따라가야 한다.
2. **논문 구조와도 맞다.** 논문은 Vega-Lite 자체를 §2.3(Visualization Specification Languages)에서 소개하고, facts로 옮기는 법은 §4.1(Fig. 2)에서 따로 다룬다. 두 장으로 나누는 것이 논문 흐름 그대로다.
3. **B(문장 수정)로는 부족하다.** `lead`에 정의 한 줄을 넣어도 화면의 주 영역(Demo)이 VL↔ASP 쌍이라서, 청중의 시선은 여전히 두 언어를 오간다.

**결정: A 슬라이드 추가 후 내용 보강**

**반영안**
- 기존 Part 2 앞에 새 파트를 넣는다. 이후 파트 번호가 하나씩 밀려 전체 12개 파트(Part 0~11)가 된다.

| | 새 Part 2: Vega-Lite란 | 기존 내용 → Part 3: 명세를 facts로 |
|---|---|---|
| 논문 근거 | §2.3 | §4.1, Fig. 2 |
| `lead` | "Vega-Lite는 차트를 '데이터 + mark + encoding'의 JSON으로 선언하는 고수준 문법이다." | "Draco는 Vega-Lite 명세의 JSON 중첩을 풀어 평평한 logical facts로 옮긴다." |
| `points` | ① Grammar of Graphics, ggplot2, Tableau의 VizQL에서 영감을 받은 언어 ② 단일 뷰 = mark 하나 + encoding 여러 개(field → channel, type N/O/Q/T, bin·aggregate) ③ 생략한 값(scale 등)은 컴파일러가 기본값으로 채움, 탐색과 추론에 쓰기 좋게 설계됨 | 현재 points 중 facts 대응 부분 + `channel(E,C)` 일반화 |
| `Demo` | **명세 → 차트 미니 편집기:** mark(bar / point / tick)와 x·y·color에 놓을 field를 버튼으로 바꾸면 JSON과 차트가 함께 바뀐다. | 현재 VL↔ASP 코드 쌍 그대로 |
| `detail` | 논문은 단일 뷰와 facet(row / column)만 다룸 / layer, concat은 범위 밖(§2.3) | 현재 detail(데이터 스키마, 과업 predicate) |

- **범위 규칙:** 새 Demo는 2019년 Draco가 쓰던 Vega-Lite v2에도 있던 기능만 쓴다(위 mark, x·y·color·size·shape·row·column 채널, bin, aggregate). 차트를 그리는 라이브러리는 현재 버전이라는 점을 기존 캡션처럼 밝힌다.
- **함께 고칠 것**
  - `sections.tsx`: 새 파트 추가, Part 3 이후 `num` 재번호
  - `docs/03_outline.md`: 목차 표, 세부 구성, 시간 배분. 새 파트 1:00을 추가하고, 기존 Vega-Lite 파트를 1:30에서 1:00으로 줄여 전체 약 15분 30초
  - `07_script.md`: 파트 하나 추가
  - 번호가 바뀌므로 다른 문서와 사이트 안의 "Part N" 참조를 모두 점검한다(IMP-001 대본의 "Part 5"는 "Part 6"이 된다).
  - 이미 공유한 `?slide=` 링크는 한 칸씩 밀린다. 아직 공유 전이라 영향은 없다.
- `01_Paper Core concepts`의 "2. Vega-Lite grammar" 절을 새 파트의 재료로 쓴다(내용 추가 없음).
