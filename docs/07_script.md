# 07. 발표 대본

화면에는 두지 않고 말로 전하는 내용을 파트별로 적는다. 화면 문구를 그대로 읽지 않고, 화면에 없는 연결·안내·강조를 말한다. `06_improvements.md`에서 방향 C(대본에만 반영)로 정한 항목과, A·B에 딸린 대본 작업이 여기에 들어간다.

## 작성 규칙

- 파트 번호와 제목은 `03_outline.md`의 목차와 같게 유지한다. 목차가 바뀌면 이 문서의 제목도 함께 바꾼다.
- 각 파트는 **시간**, **대본**, **화면 조작**(무엇을 누르고 보여 줄지), **출처 메모**(근거가 되는 §, IMP 번호)로 쓴다.
- 대본은 말하는 문장으로 쓴다. 논문에 없는 내용을 말할 때는 "제 생각에는"처럼 리뷰어 의견임을 밝힌다.
- 시간은 목차의 배분을 따르고, 합계가 16분 안팎이 되게 한다. 분량은 1분에 약 300음절(공백·기호 제외 한글 기준)로 어림한다.

### Part 1. 문제: 지침과 도구 사이의 간극 (1:00)
- 대본:
  > 먼저 문제입니다. 좋은 시각화 원칙은 책과 논문에 많이 나와 있지만, 설계자가 실제로 그 원칙을 늘 따르지는 않습니다. 그래서 원칙을 대신 적용해 주는 자동 설계 도구가 나왔습니다. 1986년 Mackinlay의 APT가 대표적입니다.
  >
  > 그런데 문제가 두 가지 있습니다. 첫째, 사람이 차트를 어떻게 읽는지에 대한 실험 결과는 계속 나오는데, 그게 도구에 들어가는 속도가 느립니다. 둘째, 도구마다 설계 지식을 자기 방식으로 따로 구현합니다. APT는 논리 규칙 약 200개로, CompassQL은 JavaScript 코드와 손으로 정한 점수로 지식을 표현했고, 서로의 지식을 가져다 쓰지 않습니다.
  >
  > 그래서 저자들은 설계 지식 자체를 여러 도구가 함께 쓰는 형식 모델로 만들자고 제안합니다. 그 형식이 제목에 있는 constraints, 즉 반드시 지킬 hard constraint와 가능하면 지킬 soft constraint입니다.
  >
  > 이걸 하려면 언어가 두 개 필요합니다. 차트를 적는 언어와 규칙을 적는 언어입니다. 차트를 적는 언어부터 보겠습니다.
- 화면 조작: 없음. 질문이 나오면 "자세히"로 APT, CompassQL, Draco 비교 표를 연다.
- 출처 메모: §1, §2.1 (APT 약 200개 규칙), §2.4 (CompassQL은 명령형 구현), IMP-004

### Part 2. Vega-Lite: 차트를 선언하는 문법 (1:00)
- 대본:
  > 차트를 적는 언어는 Vega-Lite입니다. 차트를 그리는 순서를 코드로 짜는 대신, 어떤 데이터를, 어떤 모양으로, 어떤 열을 어느 축이나 색에 놓을지만 JSON으로 적는 문법입니다. ggplot2를 써 보셨다면 같은 계열의 생각입니다.
  >
  > (데모) 오른쪽은 자동차 데이터에서 실린더 수별 평균 연비를 그린 막대 차트입니다. mark를 bar에서 point로 바꾸면, 막대 대신 차 한 대가 점 하나로 찍힙니다. color에 Origin을 넣으면 생산 지역별로 색이 나뉩니다. 바뀐 건 JSON 몇 줄뿐이고, 축과 범례와 색은 Vega-Lite가 데이터 type을 보고 알아서 채웁니다.
  >
  > 이렇게 명세가 짧고 규칙적이라서, 기계가 가능한 차트들을 탐색하고 따져 보기 좋습니다. Draco가 Vega-Lite를 고른 이유입니다. 다만 이 논문은 Vega-Lite 전체가 아니라 차트 하나와, 행이나 열로 나눈 facet 차트까지만 다룹니다.
- 화면 조작: mark를 bar → point로, color를 Origin으로 바꿔 JSON 몇 줄만 바뀌어도 차트가 달라지는 것을 보여 준다. 강조된 JSON 줄을 가리킨다.
- 출처 메모: §2.3 (영감, 탐색과 추론에 맞게 설계, 단일 뷰와 facet), §4.1 (생략한 값은 컴파일러가 추론), IMP-002, IMP-004
- 질문 대비: core concepts 7절 "Vega-Lite" (Vega/D3와의 차이, 왜 ggplot2가 아닌가, 버전)

### Part 3. Vega-Lite 명세를 facts로 (1:00)
- 대본:
  > 그런데 Draco는 이 JSON을 그대로 쓰지 않습니다. 규칙으로 추론하려면 차트를 "사실"의 목록으로 바꿔야 하기 때문입니다.
  >
  > (데모) 왼쪽이 논문 Fig. 2의 Vega-Lite 명세이고, 오른쪽이 같은 차트를 Draco의 사실로 적은 것입니다. "mark": "bar"는 mark(bar)라는 사실 하나가 됩니다. x 인코딩에는 e0라는 이름을 붙이고, e0는 x 채널이다, e0의 필드는 cylinders다, e0의 타입은 ordinal이다, 이렇게 한 줄씩 적습니다. 중첩된 JSON이 평평한 사실 목록으로 풀리는 겁니다.
  >
  > 이렇게 하는 이유는, 그래야 규칙이 "어떤 인코딩이든 nominal 필드를 size에 쓰면 안 된다"처럼 일반적으로 말할 수 있기 때문입니다. 채널마다 규칙을 따로 만들 필요가 없습니다. 데이터의 성질과 사용자가 하려는 과업도 같은 방식의 사실로 적습니다.
  >
  > 이제 이 사실들 위에 규칙을 적을 언어가 필요합니다. 그게 다음 파트의 Answer Set Programming입니다.
- 화면 조작: 왼쪽 `"mark": "bar"` 줄, 이어서 `"x": {` 줄에 마우스를 올려 오른쪽 ASP 줄이 강조되는 것을 보여 준다.
- 출처 메모: §4.1, Fig. 2 (channel(E,C) 일반화, 데이터 스키마와 과업 predicate), §4.2.1 (nominal을 size에 쓰지 않는 hard constraint), IMP-004
- 질문 대비: core concepts 7절 "왜 JSON을 facts로 바꾸나요?"
