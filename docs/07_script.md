# 07. 발표 대본

화면에는 두지 않고 말로 전하는 내용을 파트별로 적는다. 화면 문구를 그대로 읽지 않고, 화면에 없는 연결·안내·강조를 말한다. `06_improvements.md`에서 방향 C(대본에만 반영)로 정한 항목과, A·B에 딸린 대본 작업이 여기에 들어간다.

## 작성 규칙

- 파트 번호와 제목은 `03_outline.md`의 목차와 같게 유지한다. 목차가 바뀌면 이 문서의 제목도 함께 바꾼다.
- 각 파트는 **시간**, **대본**, **화면 조작**(무엇을 누르고 보여 줄지), **출처 메모**(근거가 되는 §, IMP 번호)로 쓴다.
- 대본은 말하는 문장으로 쓴다. 논문에 없는 내용을 말할 때는 "제 생각에는"처럼 리뷰어 의견임을 밝힌다.
- 시간은 목차의 배분을 따르고, 합계가 16분 안팎이 되게 한다. 분량은 1분에 약 300음절(공백·기호 제외 한글 기준)로 어림한다.

### Part 1. 문제: 지침과 도구 사이의 간극 (1:00)
- 대본:
  > 먼저 문제입니다. 좋은 시각화 원칙은 책과 논문에 많이 나와 있지만, 설계자가 실제로 그 원칙을 늘 따르지는 않습니다. 그래서 원칙을 대신 적용해 주는 자동 설계 도구가 나왔습니다. 1986년 Mackinlay의 APT가 대표적입니다.
  >
  > 그런데 문제가 두 가지 있습니다. 첫째, 사람이 차트를 어떻게 읽는지에 대한 실험 결과는 계속 나오는데, 그게 도구에 들어가는 속도가 느립니다. 둘째, 도구마다 설계 지식을 자기 방식으로 따로 구현합니다. APT는 논리 규칙 약 200개로, CompassQL은 JavaScript 코드와 손으로 정한 점수로 지식을 표현했고, 서로의 지식을 가져다 쓰지 않습니다.
  >
  > 그래서 저자들은 설계 지식 자체를 여러 도구가 함께 쓰는 형식 모델로 만들자고 제안합니다. 그 형식이 제목에 있는 constraints, 즉 반드시 지킬 hard constraint와 가능하면 지킬 soft constraint입니다.
  >
  > 이걸 하려면 언어가 두 개 필요합니다. 차트를 적는 언어와 규칙을 적는 언어입니다. 차트를 적는 언어부터 보겠습니다.
- 화면 조작: 없음. 질문이 나오면 "자세히"로 APT, CompassQL, Draco 비교 표를 연다.

### Part 4. 규칙을 쓰는 언어: ASP (1:00)
- 대본:
  > 규칙을 적는 언어는 Answer Set Programming, 줄여서 ASP입니다. 이것도 선언형 언어라서, 답을 어떻게 찾을지가 아니라 무엇이 참이고 무엇이 안 되는지만 적습니다. 그러면 solver가 조건을 모두 만족하는 답을 찾아 주는데, 그 답을 answer set이라고 부릅니다. Draco는 Clingo라는 solver를 씁니다.
  >
  > 문법은 세 가지만 기억하시면 됩니다. 첫째, "A :- B, not C."는 B가 참이고 C를 도출할 수 없으면 A가 참이라는 규칙입니다. 여기서 not은 "거짓"이 아니라 "도출할 근거가 없다"는 뜻입니다. 둘째, 머리 없이 ":-"로 시작하면 hard constraint입니다. 이 조건이 성립하는 답은 버립니다. 셋째, ":~"로 시작하고 끝에 대괄호 숫자가 붙으면 soft constraint입니다. 답을 버리지는 않고, 그 숫자만큼 벌점을 줍니다.
  >
  > 그래서 최적의 답은 벌점 합이 가장 작은 answer set이고, Draco에서는 answer set 하나가 차트 하나입니다.
- 화면 조작: 요점의 세 줄을 차례로 가리킨다. 질문이 나오면 "자세히"로 문법 표를 연다.
- 출처 메모: §3 (rule, negation as failure, integrity constraint, soft constraint, 최적 answer set), §2.4 (Clingo)
- 질문 대비: core concepts 7절 "ASP" (Prolog와의 차이, 왜 ASP인가, answer set의 뜻)

### Part 5. 설계 공간과 hard constraints (1:30)
- 대본:
  > 이제 이 언어로 가능한 차트들의 공간을 정의합니다. (① 설계 공간) 먼저 aggregate rule로 각 속성이 가질 수 있는 값을 정합니다. 예를 들어 mark는 bar, line, area, point 중 정확히 하나입니다. 이렇게 하면 가능한 조합 전체가 후보가 됩니다.
  >
  > (② Well-formedness) 다음은 문법적으로 성립하지 않는 차트를 지웁니다. shape 채널은 point mark에만 쓸 수 있고, log scale에는 0을 넣을 수 없다는 식입니다.
  >
  > (③ Expressiveness) 그다음은 데이터의 사실을 전부, 그리고 그것만 보여 주지 못하는 차트를 지웁니다. 앞에서 예로 든 "nominal 필드를 size에 쓰지 않는다"가 여기 해당합니다. 크기는 순서를 암시하는데 nominal에는 순서가 없으니까요. 막대는 0에서 시작해야 한다는 규칙도 여기 있습니다.
  >
  > (④ Soft constraint로 정렬) 남은 후보를 soft constraint 비용으로 줄 세우면 맨 위가 최적입니다. 하나 재미있는 점은, 일부 hard constraint는 디자인 원칙이 아니라 Vega-Lite 구현의 한계라는 겁니다. shape가 8종뿐이라서 범주가 8개를 넘으면 shape를 쓸 수 없습니다.
- 화면 조작: 단계 버튼 ①→②→③→④를 말하는 순서에 맞춰 누른다. ④에서 "최적" 표시를 가리킨다.
- 출처 메모: §4.2.1 (aggregate rule 예시, well-formedness, expressiveness, size·nominal, 막대 0 기준선, shape 8종), Fig. 3

### Part 6. Soft constraints와 비용 (2:00)
- 대본:
  > 남은 후보를 줄 세우는 게 soft constraint입니다. 예를 들어 "연속형 필드는 0을 포함하는 게 좋다, 어기면 비용 5" 같은 규칙입니다. 한 차트가 같은 규칙을 인코딩마다 여러 번 어길 수 있어서, 비용은 weight 곱하기 위반 횟수를 모두 더한 값입니다. 평균이 아니라 합입니다.
  >
  > (데모) 질의는 "마력과 생산 지역을 보여 줘"입니다. 후보 다섯 개는 지역이라는 범주형 필드를 각각 다른 채널에 놓았습니다. 슬라이더의 초기값은 논문 §6.2에 나온 Draco-CQL의 weight입니다. y가 0, x가 1, row 6, color 7, shape 8입니다. 그래서 지금 1위는 지역을 y축에 둔 틱 차트입니다. (y 슬라이더를 2로) y의 weight를 2로 올리면 1위가 지역을 x축에 둔 막대 차트로 바뀝니다. weight 하나가 추천 결과를 바꿉니다.
  >
  > 여기서 문제가 보입니다. Draco-CQL만 해도 soft constraint가 110개입니다. weight 하나를 고쳤을 때 다른 질의들의 결과가 어떻게 바뀔지 사람이 다 따질 수 없습니다. 논문 표현으로는 국소적인 변경이 예상하지 못한 전역 효과를 냅니다. 그래서 뒤에서 weight를 데이터로 배우는 방법이 나옵니다.
  >
  > (토스트 가리키며) 처음에 보신 오른쪽 아래 토스트가 바로 이 계산입니다. 지금은 발표 상황이라 Deck의 비용이 가장 낮습니다.
- 화면 조작: y 슬라이더를 0 → 2로 올려 1위가 막대 차트(A)로 바뀌는 순간을 보여 준다. 마지막 문장에서 오른쪽 아래 배지를 눌러 토스트를 연다. 끝나면 "초기화"로 되돌린다.
- 출처 메모: §4.2.2 (soft constraint, 비용 = Σ weight × 위반 횟수), §6.2 (Draco-CQL nominal 채널 weight, soft 110개), §1 (local changes, global effects), IMP-001
- 질문 대비: core concepts 7절 "비용은 weight의 평균인가요?"

### Part 7. 질의에서 차트로 (1:30)

### Part 8. weight를 데이터에서 배우기: learning to rank (1:00)
- 대본:
  > 이제 논문의 두 번째 기여, weight를 데이터에서 배우는 부분입니다. 보통 추천 모델을 학습하려면 "이 질의의 정답 차트"가 있어야 하는데, 시각화는 정답이 하나로 정해지지 않습니다. 대신 지각 실험은 "같은 데이터, 같은 과업에서 차트 A가 B보다 유의하게 정확했다"는 비교 결과를 줍니다. 그래서 점수가 아니라 순서를 배웁니다.

### Part 9. RankSVM: 순위 쌍을 분류 문제로 (1:30)
- 대본:
  > 그 w를 찾는 방법이 RankSVM입니다. 아이디어는 간단합니다. 두 차트의 비용 차이는 w와 두 벡터 차이의 내적입니다. 그러면 "어느 쪽이 나은가"는 이 차이 벡터가 경계의 어느 쪽에 있느냐는 이진 분류가 됩니다. 순위 학습이 선형 SVM 분류로 바뀌는 겁니다. 손실은 hinge loss에 L2 정규화이고, 선호되는 차트의 비용이 그냥 낮은 게 아니라 1 이상 낮아야 손실이 0입니다.
  >
  > (카드를 하나씩 켜며) 실험 결과를 하나씩 넣어 보겠습니다. color가 shape보다 낫다, row가 shape보다 낫다, color가 row보다 낫다. weight가 거기에 맞게 벌어지고 세 쌍을 모두 맞힙니다. (마지막 카드) 여기에 반대 결과가 하나 섞이면 네 쌍 중 세 쌍만 맞힙니다. 실험끼리 어긋나는 결과가 있어도 전체적으로 가장 잘 맞는 weight를 찾는 겁니다.
  >
  > 중요한 건, 이렇게 학습한 w가 그대로 ASP의 soft constraint weight가 된다는 점입니다. 새 규칙을 추가하면 weight 0에서 시작해 다시 학습하면 됩니다.
- 화면 조작: 카드 1 → 2 → 3을 켜 쌍 정확도 3/3을 보여 주고, 마지막 "상충하는 결과" 카드를 켜 3/4로 떨어지는 것을 짚는다.
- 출처 메모: §5 (f = wᵀ(x1 − x2), hinge + L2, λ = 0.1, 대칭성), §6.3 (scikit-learn SVM, 새 규칙은 weight 0), IMP-003
- 질문 대비: core concepts 7절 "RankSVM" ("linear regression"이라는 표현, y = −1로 통일, 음수 weight)

### Part 10. 증거: APT → CQL → Learn (2:00)
- 대본:
  > 그럼 이게 실제로 되는지, 논문은 세 단계로 보여 줍니다.
  >
  > 첫째, Draco-APT입니다. APT의 "중요한 필드부터 가장 좋은 채널을 준다"는 원칙을 우선순위가 붙은 soft constraint로 재현했습니다.
  >
  > 둘째, Draco-CQL입니다. (타일) CompassQL을 다시 구현했더니 테스트 질의 17개에서 모두 같은 최적 명세를 냈고, JavaScript 4,324줄이 제약 180개로 줄었습니다. 속도도 다릅니다. 필드 25개, 인코딩 5개 질의를 0.5초 안에 푸는데, CompassQL은 몇 분 뒤 메모리가 부족해 멈췄습니다. 모든 조합을 만든 뒤 검사하는 방식과 solver 탐색의 차이입니다.
  >
  > 셋째, Draco-Learn입니다. 두 지각 실험에서 모은 순위 쌍으로 weight를 학습했더니 테스트 쌍의 순서 정확도가 93%였고, 손으로 정한 Draco-CQL은 65%였습니다.
  >

### Part 11. 평가: 강점과 한계 (1:30)
- 대본:
